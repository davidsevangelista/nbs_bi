1. Problem

NBS has 16,491 registered users with radically different behavioral profiles: some are high-volume onrampers generating meaningful spread revenue, others are DeFi traders who never converted BRL, others registered and never opened the app again. The existing segmentation (champion / active / at_risk / dormant) classifies users only by recency and revenue — it cannot distinguish how users use the product.

This means push notification campaigns cannot be targeted by product behavior. A DeFi trader receives the same message as a dormant user who never completed KYC. The result is low notification read rates and wasted send quota on users who will never convert from a generic message.

This project replaces that coarse classification with an ML-derived segmentation — mapping each user to a behavioral archetype — so that push campaigns can be targeted by product usage pattern, recency, and revenue profile simultaneously.

2. Approach

Feature extraction — 37 behavioral signals per user Six groups: lifecycle (signup age, onboarding status), onramp/offramp (volume, revenue, recency), card (spend, annual fee), DeFi/Solana (swaps, token diversity), international payouts, and engagement (AI sessions, notification read rate). All extracted directly from the production DB. No PII.
Preprocessing — log transform → StandardScaler → PCA Financial data follows power-law distributions: a minority of users has extreme volume. log1p compresses the tail without losing zeros. StandardScaler normalises scale. PCA (retaining 90% of variance) reduces 37 features to 12 components, eliminating redundant signals and stopping high-variance features like total_onramp_brl from dominating the distance metric used by K-Means.
Outlier quarantine — HDBSCAN Before clustering, users with extreme or anomalous profiles are detected and quarantined using HDBSCAN (density-based outlier detection). 4,026 users (24.4%) were removed — likely test accounts, bots, or VIP accounts with unique behaviour patterns that would otherwise distort cluster centroids.
K selection — silhouette score, Davies-Bouldin index, inertia elbow K-Means was run for k = 4 through 11. Three independent metrics were evaluated to select the optimal number of clusters. k = 8 maximised the silhouette score (0.514) — the clearest behavioural separation achievable in this user base.
Final clustering — K-Means with GMM validation and seed stability K-Means (k = 8, 20 restarts with k-means++ initialisation) was the primary algorithm. Results were cross-validated against a Gaussian Mixture Model. Stability was confirmed by re-running across 5 different random seeds — the min pairwise ARI was 0.994, meaning the cluster structure is essentially deterministic.
Export — CSV with per-segment Brazilian Portuguese push copy 6,938 pushable users (active device token + delivery rules applied) exported with segment name, cluster ID, kyc_level, and ready-to-send push copy (title + body) for three time-of-day slots (morning, afternoon, evening) in Brazilian Portuguese.

3. Cluster Count Selection

Three metrics were evaluated across k = 4–11. The silhouette score measures how cleanly each user is assigned to its cluster versus the nearest alternative (higher = better, target > 0.25). The Davies-Bouldin index measures within-cluster scatter relative to between-cluster distance (lower = better). The inertia elbow identifies where adding more clusters yields diminishing returns.

6. KYC-Level-0 Override

Across all segments, users with kyc_level ≤ 1 (not yet fully verified) receive a dedicated KYC completion CTA regardless of their cluster assignment — the generic segment message is irrelevant to a user who has not completed verification. kyc_level = 2 means fully verified; those users always receive their segment copy. This override is applied in the CSV export: the backend reads kyc_level directly from the export and applies the appropriate copy.

Why as a delivery layer rule, not a cluster? kyc_level was removed from the clustering features entirely — in the NBS user base it is effectively binary (0 = never transacted, 2 = transacted), making it collinear with every activity feature. Including it in the feature matrix would double-count information already captured by onboarding_completed, n_onramp_txns, and the binary presence flags. It is retained as a metadata column in the export solely to drive this message override.

7. Why PCA Before K-Means

The 37 input features were reduced to 12 principal components retaining 90.4% of total variance before clustering. This is not a data reduction convenience — it is required for K-Means to work correctly on this data:

  • Correlated features inflate distance. n_onramp_txns and total_onramp_brl are highly correlated. Without PCA, both count in the Euclidean distance metric, effectively weighting onramp behaviour double relative to card or DeFi activity.
  • High-variance features dominate. total_onramp_brl spans a far larger range than n_ai_sessions. Even after StandardScaler, residual correlation causes dominant features to overwhelm meaningful low-variance signals like has_card or n_unique_tokens.
  • Curse of dimensionality. In high-dimensional spaces, Euclidean distances lose discriminative power — all points become approximately equidistant. Reducing to 12 components puts the geometry back in a regime where distance is meaningful.

8. The 4,026 Quarantined Users

24.4% of users were removed before clustering. This is high but expected: HDBSCAN operates in the PCA-compressed space and flags users whose behavioral profile does not fit into any density region shared by at least 15 other users. The outlier distribution shows:

  • High variance in card spend (std R$2,142 vs mean R$218) — a small number of extremely high spenders
  • High variance in swap count (std 12.4 vs mean 1.3) — DeFi power users with extreme transaction counts
  • High Solana transaction counts (mean 6 txns, but std 33) — likely bots or automated wallets

These users are excluded from the cluster export. Campaigns should not target them with automated push — they require manual review and dedicated treatment.

9. Monthly Refresh Protocol

The clustering artifacts (scaler, PCA, K-Means model, segment name mapping) are saved to data/processed/ and versioned by month. New users can be scored without re-fitting: apply the saved scaler → PCA → km.predict().

A full re-fit (re-running the entire notebook Sections 3–6) should be done once per quarter, or when the user base grows by more than 20%. After a full re-fit, cluster IDs will shift — the segment name mapping must be manually re-reviewed against the heatmap.
