1. Problem

NBS has 16,499 registered users with radically different behavioral profiles: some are high-volume onrampers generating meaningful spread revenue, others are DeFi traders who never converted BRL, others registered and never opened the app again. The existing segmentation (champion / active / at_risk / dormant) classifies users only by recency and revenue — it cannot distinguish how users use the product.

This project replaces that coarse classification with an ML-derived segmentation — mapping each user to a behavioral archetype — so that push campaigns can be targeted by product usage pattern, recency, and revenue profile simultaneously.

2. Feature Engineering

One row per user. 37 numeric features extracted directly from the production DB — no PII, user_id is the only identifier. kyc_level is excluded from clustering inputs (it is binary in this user base: 0 = unverified, 2 = verified, collinear with all activity features) and kept as a metadata column for the KYC override rule.

3. Approach

Feature extraction — 37 behavioral signals per user Six groups: lifecycle (signup age, onboarding status), onramp/offramp (volume, revenue, recency), card (spend, annual fee), DeFi/Solana (swaps, token diversity), international payouts, and engagement (AI sessions, notification read rate). Extracted directly from the production DB. No PII. Note: kyc_level is excluded from clustering features — it is effectively binary in this user base (0 = unverified, 2 = verified), collinear with all activity features. It is kept as a metadata column to drive the KYC-override messaging rule.
Preprocessing — log transform → StandardScaler → PCA Financial data follows power-law distributions. log1p compresses the tail without losing zeros. StandardScaler normalises scale across features. PCA retains 90.3% of variance in 12 components, eliminating correlated signals and preventing high-variance features from dominating the distance metric.
Outlier detection — HDBSCAN (flag only, no removal) HDBSCAN identifies 4,064 users (24.6%) whose behavioral profile sits in low-density regions of the PCA space. These are flagged as is_outlier=1 in the export but remain in the clustering — removing them would exclude high-volume kyc_level=2 users who are precisely the most valuable segment. PCA compression makes K-Means robust enough to handle them without distortion.
K selection — silhouette score, Davies-Bouldin index, inertia elbow K-Means evaluated for k = 4–11. k = 7 maximised the silhouette score (0.000) — the clearest behavioural separation achievable in this user base.
Final clustering — K-Means + GMM validation + seed stability K-Means (k = 7, 20 restarts with k-means++ initialisation). Cross-validated against GMM (ARI = 0.543). Stability confirmed across 5 seeds — min pairwise ARI = 0.981.
Export — CSV with per-segment Brazilian Portuguese push copy All 16,499 clustered users exported with segment name, cluster ID, kyc_level, and push copy (title + body) for three time-of-day slots in Brazilian Portuguese. Three delivery metadata flags are included so the backend controls targeting: is_pushable (has active device token), skip_push (dormant with zero notification engagement — use email/SMS in Phase 2), is_outlier (extreme profile — review before sending). Users with kyc_level ≤ 1 receive a KYC completion CTA regardless of cluster.

7. KYC Override Rule

Users with kyc_level ≤ 1 (not yet fully verified) receive a dedicated KYC completion CTA regardless of their cluster assignment — the generic segment message is irrelevant to a user who has not completed verification. kyc_level = 2 means fully verified; those users always receive their segment copy.

Why as a delivery-layer rule, not a cluster? kyc_level was removed from clustering features — it is effectively binary in this user base (0 or 2), collinear with onboarding_completed and every activity feature. Including it would double-count information already captured by presence flags and transaction counts. It is retained as a metadata column in the export solely to drive this override.

8. Why PCA Before K-Means

The 37 input features were reduced to 12 principal components retaining 90.3% of total variance before clustering. This is required for K-Means to work correctly on this data:

  • Correlated features inflate distance. n_onramp_txns and total_onramp_brl are highly correlated — without PCA, both count in the Euclidean distance, effectively double-weighting onramp behaviour.
  • High-variance features dominate. Even after StandardScaler, residual correlation causes dominant features to overwhelm low-variance but meaningful signals like has_card or n_unique_tokens.
  • Curse of dimensionality. In high-dimensional spaces, Euclidean distances lose discriminative power. Reducing to 12 components restores meaningful geometry.

9. Outlier Flags — is_outlier

4,064 users (24.6%) are flagged as statistical outliers by HDBSCAN — their behavioral profile does not share a density region with at least 15 other users. Typical profiles: extreme-volume onrampers, DeFi power users with automated swap counts, possible internal test accounts.

These users are included in clustering and in the export. The is_outlier=1 flag lets the backend apply extra caution — e.g. manual review before sending, or excluding from automated bulk campaigns — without losing them from the CRM dataset entirely. Previous versions removed them, which caused kyc_level=2 high-value users to disappear from the export.

10. Monthly Refresh Protocol

Clustering artifacts (scaler, PCA, K-Means model, segment name mapping) are saved to data/processed/ versioned by month. New users can be scored without re-fitting: apply saved scaler → PCA → km.predict().

A full re-fit should run once per quarter or when the user base grows by more than 20%. After a full re-fit, cluster IDs shift — the segment name mapping must be manually re-reviewed against the heatmap.
